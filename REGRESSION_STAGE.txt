CARRERA-HUB REGRESSION STAGE 4R5-A
==================================
Name: Recovery Trigger Instrumentation

Baseline: Stage 4R4 - Dashboard Resize & Table Layout Hardening
Parent experiment: Stage 4R4

Purpose:
- Diagnose the newly observed clienu recovery loop after simultaneous
  force-close of multiple packages.
- Determine whether the second recovery is caused by a false PID mismatch,
  duplicate recovery worker, stale tracked PID, or a recovery-state timing race.

Behavioral policy:
- NO recovery algorithm or timing change in this stage.
- NO state-guard fix in this stage.
- The existing 30-second minimum single-package recovery delay is preserved.
- Dashboard rendering is untouched.

Instrumentation added:
1. Watchdog logs every recovery trigger with package, reason, expected PID,
   observed PID, and current status.
2. Each single recovery worker logs its thread identity and lifecycle.
3. Recovery worker logs state/PID before and after the 30-second delay.
4. Each recovery tier logs entry/exit context, current PID, tracked PID,
   baseline PID, and visible state.
5. Recovery success/failure is logged with worker identity so duplicate or
   overlapping workers can be identified.
6. Trigger requests are logged before a recovery worker is spawned.

Test focus:
1. Start 2 packages normally.
2. Force-close clienu + clienv simultaneously.
3. Wait until both reach Farming.
4. Observe whether clienu produces another RECOVERY trigger without a genuine
   process loss.
5. Repeat with reversed order and with only one package interrupted.
6. Inspect logs/latest.log for [WATCHDOG] and [RECOVERY-TRACE] entries.
7. For 5-7 packages, verify no duplicate workers are created during one
   recovery event.

Expected diagnostic result:
- We should be able to identify the exact trigger and PID transition that
  causes any unexpected Farming -> Recovery -> Loading -> Farming loop.

Status:
Experimental. NOT baseline until user testing passes.
